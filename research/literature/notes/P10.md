## Paper Metadata
- **Title**: Benchmarks and Metrics for Evaluations of Code Generation: A Critical Review
- **Source**: IEEE AITest 2024 (TELLMe Workshop on Testing and Evaluation of Large Language Models)
- **arXiv ID**: 2406.12655
- **Date**: Submitted June 18, 2024
- **Authors**: Debalina Ghosh Paul, Hong Zhu, Ian Bayley
- **Institution**: School of Engineering, Computing and Mathematics, Oxford Brookes University

## Key Findings

1. **Open Problem Identified**: "How to evaluate such LLMs for this task is still an open problem" despite considerable research
2. **Two Critical Aspects**: Systematic examination of benchmarks and metrics used in comparative studies
3. **HumanEval Limitations**: Widely adopted but has significant constraints limiting real-world applicability
4. **Metric Issues**: Traditional metrics (BLEU, ROUGE, METEOR) focus on surface similarity, not functional correctness
5. **Pass@k Bias**: Single-attempt (pass@1) metrics don't capture multi-attempt success capabilities

## Benchmark Limitations Identified

**HumanEval**:
- Test adequacy issues - limited corner case coverage (though HumanEval+ claims comprehensive coverage)
- Security concerns - pre-scripted test cases detect only errors of omission, not commission (malicious code)
- Data leakage from widespread use in training

**General Benchmark Problems**:
- Narrow task scope (standalone functions vs. real-world complexity)
- Language specificity - metrics designed for natural language fail on code syntax
- Lack of multi-dimensional assessment (only correctness, not quality/efficiency/readability)

## Metric Problems Identified

**Syntactic vs. Semantic Assessment**:
- Text similarity metrics (BLEU, ROUGE, METEOR) inadequate for code
- Need execution-based evaluation (functional correctness)

**pass@k Limitations**:
- pass@k = "probability of getting at least one correct solution in k outputs"
- Reflects LLM output randomness but doesn't assess reasoning quality
- Single-attempt bias (pass@1) common but incomplete

**Correctness Measurement Approaches**:
- Reference solutions (ConCode) - template matching
- Test cases (HumanEval, MBPP, MathQA-Python, MultiPL-E)
- Combination (APPS, ClassEval, CoderEval, DS-1000)

## Design Implications

1. **Better Benchmarks Needed**: LLM-friendly language validation requires comprehensive, multi-dimensional benchmarks
2. **Functional Correctness Priority**: Language features should enable execution-based testing
3. **Multi-Dimensional Metrics**: Beyond syntax - measure correctness, quality, efficiency, readability
4. **Task-Specific Evaluation**: Different problem types need different assessment approaches
5. **Security-Aware Testing**: Language should facilitate detection of commission errors (malicious code)

## Relevant Quotes

> "how to evaluate such LLMs for this task is still an open problem"

> "Correctness of generated code is the main quality attribute for assessing the response of an LLM to a programming task"

> "pass@k, the probability of getting at least one correct solution in k outputs, reflects the randomness of the LLM output"

> "pre-scripted test cases can detect only errors of omission, as opposed to errors of commission, which can include malicious code"
