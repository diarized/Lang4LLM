**Status**: Analyzed (Abstract and arXiv page)

## Paper Metadata
- **Title**: What's Wrong with Your Code Generated by Large Language Models? An Extensive Study
- **Source**: arXiv preprint
- **arXiv ID**: 2407.06153
- **Date**: Submitted July 8, 2024; Last revised October 17, 2025 (v2)
- **Authors**: Shihan Dou, Haoxiang Jia, Shenxi Wu, Huiyuan Zheng, Muling Wu, Yunbo Tao, Ming Zhang, Mingxu Chai, Jessica Fan, Zhiheng Xi, Rui Zheng, Yueming Wu, Ming Wen, Tao Gui, Qi Zhang, Xipeng Qiu, Xuanjing Huang (17 authors)

## Key Findings

1. **Comprehensive Bug Taxonomy**: 3 major categories, 10 sub-categories with root cause analysis
2. **Large-Scale Evaluation**: 3 closed-source + 6 open-source LLMs tested on 3 benchmarks
3. **Real-World vs Lab Gap**: Real-world benchmark (RWPB) shows distinct bug distributions compared to lab benchmarks
4. **Self-Repair Capability**: Self-critique method achieves 29.2% repair success rate after two iterations
5. **Code Quality Characteristics**: LLMs produce shorter but more complicated code than canonical solutions
6. **Bug Distribution Variance**: Different benchmarks reveal different bug patterns, highlighting context dependency

## Error Patterns Identified

**Three Major Categories** with 10 sub-categories (specific breakdown requires full paper):

**Root Cause Analysis Approach**:
- Why bugs occur (causal factors)
- How bugs manifest (symptoms)
- Where bugs appear (localization)

**Real-World Benchmark (RWPB) Findings**:
- Distinct bug distributions vs HumanEval/MBPP
- Real-world scenarios expose different failure modes
- Lab benchmarks may not capture production error patterns

**Code Complexity Patterns**:
- Shorter code length than canonical solutions
- Higher complexity despite shorter length
- Complexity-bug correlation (likely)

## Design Implications

1. **Complexity Reduction Features**: Language should enable simple, readable solutions over complex short ones
2. **Self-Correction Support**: Built-in features that enable LLMs to critique and repair their own code
3. **Context-Aware Syntax**: Different contexts (lab vs real-world) need different language support
4. **Explicitness Over Brevity**: Encourage verbose but clear code rather than terse complicated code
5. **Root Cause Visibility**: Language constructs that make error causes transparent
6. **Benchmark Diversity Awareness**: Language design validated against multiple benchmark types
