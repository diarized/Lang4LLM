# BS-M-005: Validate Email Address

**Tier**: Medium
**Category**: String Processing
**Estimated LOC**: 30-45

## Task Description

Validate whether a given string is a properly formatted email address according to basic email format rules.

## Requirements

### Functional Requirements

1. Accept a string as input
2. Check if it matches basic email format
3. Return true if valid, false otherwise
4. Validate structure, not deliverability

### Email Format Rules

A valid email must have:
1. One '@' symbol (exactly one)
2. Local part before '@' (username):
   - At least 1 character
   - Contains only letters, numbers, dots (.), underscores (_), hyphens (-)
   - Cannot start or end with a dot
   - No consecutive dots
3. Domain part after '@':
   - At least one dot separating domain and TLD
   - Domain contains only letters, numbers, hyphens
   - TLD (top-level domain) is at least 2 characters, letters only
   - No consecutive dots

### Input Specification

- **email**: A string to validate
- **Return**: Boolean (true if valid email format, false otherwise)

### Constraints

- Email length: 1 to 320 characters
- Case-insensitive validation (email@example.com and EMAIL@EXAMPLE.COM both valid)
- Do not use regex libraries (implement validation logic directly)
- Time complexity: O(n) where n is string length

## Examples

### Example 1: Valid simple email

**Input**: "user@example.com"
**Output**: true
**Explanation**: Matches all format rules

### Example 2: Valid with numbers and dots

**Input**: "john.doe123@mail.company.com"
**Output**: true
**Explanation**: Letters, numbers, dots in local; multi-part domain

### Example 3: Invalid - no @

**Input**: "userexample.com"
**Output**: false
**Explanation**: Missing @ symbol

### Example 4: Invalid - multiple @

**Input**: "user@@example.com"
**Output**: false
**Explanation**: Cannot have multiple @ symbols

### Example 5: Invalid - no domain

**Input**: "user@"
**Output**: false
**Explanation**: No domain after @

### Example 6: Invalid - no TLD

**Input**: "user@example"
**Output**: false
**Explanation**: Domain must have at least one dot for TLD

### Example 7: Invalid - starts with dot

**Input**: ".user@example.com"
**Output**: false
**Explanation**: Local part cannot start with dot

### Example 8: Invalid - consecutive dots

**Input**: "user..name@example.com"
**Output**: false
**Explanation**: No consecutive dots allowed

### Example 9: Invalid - TLD too short

**Input**: "user@example.c"
**Output**: false
**Explanation**: TLD must be at least 2 characters

### Example 10: Valid with underscores

**Input**: "user_name@example.com"
**Output**: true
**Explanation**: Underscores allowed in local part

## Notes

**Validation Strategy**:
1. Check for exactly one '@' symbol
2. Split string at '@' into local and domain parts
3. Validate local part:
   - Check length > 0
   - Check allowed characters
   - Check no leading/trailing/consecutive dots
4. Validate domain part:
   - Check contains at least one dot
   - Check domain portion (before last dot)
   - Check TLD portion (after last dot, ≥2 chars)

**Common Mistakes**:
- Not checking for exactly one @ (allowing 0 or 2+)
- Not validating dot positions (leading, trailing, consecutive)
- Not checking TLD length
- Allowing invalid characters
- Not splitting validation into local and domain parts
- Using overly complex regex (avoid for this task)

**Simplifications**:
- This is basic validation, not RFC 5322 compliant
- Does not check for quoted strings or special cases
- Does not validate actual domain existence
