# BS-M-040: Task Queue

**Tier**: Medium
**Category**: Concurrency
**Estimated LOC**: 45-60

## Task Description

Implement a bounded task queue where producer threads add tasks and consumer threads retrieve and process them. The queue has a fixed maximum capacity and must block producers when full and block consumers when empty, coordinating safely between concurrent producers and consumers.

## Requirements

### Functional Requirements

1. **enqueue(task)**: Add a task to the queue
   - If the queue is at maximum capacity, block (wait) until space becomes available
   - Once space is available, add the task and return
2. **dequeue()**: Remove and return the next task from the queue (FIFO order)
   - If the queue is empty, block (wait) until a task becomes available
   - Returns the task value
3. **try_enqueue(task, timeout)**: Attempt to add a task within a time limit
   - If space becomes available within timeout duration, add the task and return true
   - If timeout expires before space is available, return false without modifying the queue
4. **size()**: Return the current number of tasks in the queue
5. **is_empty()**: Return true if the queue contains no tasks
6. **is_full()**: Return true if the queue is at maximum capacity
7. Create the queue with a specified maximum capacity (positive integer)

### Concurrency Requirements

- Multiple producers may call enqueue() concurrently — no tasks lost, no corruption
- Multiple consumers may call dequeue() concurrently — each task returned to exactly one consumer
- Producers block (not busy-wait) when queue is full
- Consumers block (not busy-wait) when queue is empty
- When a producer adds a task to a previously empty queue, a waiting consumer must be notified
- When a consumer removes a task from a previously full queue, a waiting producer must be notified

### Input Specification

- **capacity**: A positive integer — maximum number of tasks the queue can hold simultaneously
- **enqueue(task)**: Any value — the task to add; blocks if full
- **dequeue()**: No parameters; returns any value — the next task; blocks if empty
- **try_enqueue(task, timeout)**: task — any value; timeout — duration in milliseconds; returns boolean
- **size()**: Returns non-negative integer
- **is_empty()**: Returns boolean
- **is_full()**: Returns boolean

### Constraints

- Capacity: 1 to 1,000 tasks
- FIFO ordering: tasks are dequeued in the order they were enqueued
- Tasks may be of any type
- No busy-waiting: use condition variables, semaphores, or equivalent blocking primitives
- The queue does not process tasks itself — it only stores and transfers them between threads

## Examples

### Example 1: Basic single-producer single-consumer

**Setup**: Queue with capacity 3
**Operations** (sequential):
- enqueue("task_1") → size() = 1
- enqueue("task_2") → size() = 2
- dequeue() → "task_1", size() = 1
- dequeue() → "task_2", size() = 0

**Explanation**: FIFO order maintained; size updates correctly

### Example 2: Queue fills to capacity

**Setup**: Queue with capacity 2
**Operations** (sequential):
- enqueue("A") → is_full() = false
- enqueue("B") → is_full() = true
- (A third enqueue would block until a consumer dequeues)

**Explanation**: After two enqueues with capacity 2, queue is full

### Example 3: Consumer blocks until producer enqueues

**Setup**: Queue with capacity 5; start consumer thread calling dequeue(); queue is empty
**Action**: Producer (in separate thread) enqueues "task_1" after 100ms
**Result**: Consumer receives "task_1" after the producer adds it
**Explanation**: Consumer blocks on empty queue; producer's enqueue unblocks consumer

### Example 4: Producer blocks until consumer dequeues

**Setup**: Queue with capacity 1; enqueue("first") fills it
**Action**: Producer (in separate thread) tries enqueue("second"); consumer (in another thread) calls dequeue() after 100ms
**Result**: Producer's enqueue completes after consumer's dequeue frees space; consumer receives "first"
**Explanation**: Producer blocks on full queue; consumer's dequeue unblocks producer

### Example 5: Multiple producers and consumers

**Setup**: Queue with capacity 10; 3 producer threads each enqueue 100 tasks; 3 consumer threads each dequeue 100 tasks
**Result**: All 300 tasks are transferred; each task delivered to exactly one consumer; no tasks duplicated or lost

**Explanation**: Concurrent producers and consumers coordinate correctly via the queue

### Example 6: try_enqueue with timeout

**Setup**: Queue with capacity 1; queue is full
**Action**: try_enqueue("extra", timeout=50ms)
**Result**: Returns false (queue remains full; no consumer dequeues within 50ms)
**Explanation**: try_enqueue respects the timeout and does not block indefinitely

### Example 7: FIFO ordering verified

**Setup**: Queue with capacity 5; single producer enqueues "A", "B", "C"; single consumer dequeues three times
**Result**: Receives "A", then "B", then "C"
**Explanation**: FIFO ordering guarantees tasks dequeued in insertion order

- is_empty() true when empty, false otherwise
- is_full() true at capacity, false otherwise
- Consumer blocks on empty queue until producer enqueues

- Concurrent producers: all tasks enqueued without loss

## Success Criteria

- [ ] FIFO ordering preserved
- [ ] No tasks lost under concurrent producer access
- [ ] No task delivered to more than one consumer
- [ ] Producers block (not busy-wait) when queue is full
- [ ] Consumers block (not busy-wait) when queue is empty

## Notes

**Common Mistakes**:
- Busy-waiting (spinning in a loop checking the queue state) — wastes CPU and is not acceptable; use blocking primitives
- Not notifying waiting threads after state changes — a producer that adds to an empty queue must signal waiting consumers; a consumer that removes from a full queue must signal waiting producers
- Using a single condition variable for both "not full" and "not empty" — leads to spurious wakeups notifying the wrong waiters; use two separate condition variables or equivalent
- Not using FIFO ordering for the internal buffer (use a queue, not a stack)
- Race condition on size() — size must be read under the same lock used for enqueue/dequeue

**Synchronization Pattern** (mutex + two condition variables):
- mutex: protects the queue and size
- not_full: producers wait on this when queue is full; consumers signal this after dequeuing
- not_empty: consumers wait on this when queue is empty; producers signal this after enqueuing

**try_enqueue Implementation**: Use a timed wait on the not_full condition variable. If the wait returns due to timeout without the condition being satisfied, return false.

**Language Note**: The spec is language-agnostic. Use the blocking queue, channel, or mutex+condvar primitives available in the target language.
