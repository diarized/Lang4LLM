# BS-M-038: Event Dispatcher

**Tier**: Medium
**Category**: Object-Oriented Design
**Estimated LOC**: 40-55

## Task Description

Implement an event dispatcher that allows handlers (functions or callable objects) to be registered for named events and invoked when those events are dispatched. Multiple handlers may be registered for the same event, and all registered handlers are called in registration order when the event is dispatched.

## Requirements

### Functional Requirements

1. **subscribe(event_name, handler)**: Register a handler for a named event
   - event_name is a string identifying the event
   - handler is a callable that accepts one argument (the event data)
   - Multiple handlers may be subscribed to the same event
   - The same handler may be subscribed multiple times (each subscription is independent)
2. **dispatch(event_name, data)**: Trigger all handlers registered for the event
   - Calls each registered handler for event_name in the order they were subscribed
   - Passes data as the single argument to each handler
   - If no handlers are registered for event_name, dispatch does nothing (no error)
   - Returns nothing (void)
3. **unsubscribe(event_name, handler)**: Remove one registration of the handler for the event
   - If the same handler was subscribed multiple times, removes only the first occurrence
   - If the handler is not registered for the event, does nothing (no error)
4. **clear(event_name)**: Remove all handlers registered for the event
   - If no handlers are registered for the event, does nothing

### Input Specification

- **subscribe(event_name, handler)**: event_name is a string; handler is a callable taking one argument
- **dispatch(event_name, data)**: event_name is a string; data is any value passed to handlers
- **unsubscribe(event_name, handler)**: event_name is a string; handler is the same callable previously subscribed
- **clear(event_name)**: event_name is a string

### Constraints

- Handlers are called synchronously in the order they were subscribed
- event_name strings are case-sensitive
- No limit on the number of events or handlers (within available memory)
- Handler exceptions/errors: behavior is undefined (not required to be caught)
- Data passed to dispatch may be of any type

## Examples

### Example 1: Single handler

**Operations**:
- results = []
- subscribe("click", handler that appends data to results)
- dispatch("click", "button_1")
- results → ["button_1"]

**Explanation**: One handler registered; dispatch calls it once with the data

### Example 2: Multiple handlers for same event

**Operations**:
- log = []
- subscribe("login", handler_A that appends "A:" + data to log)
- subscribe("login", handler_B that appends "B:" + data to log)
- dispatch("login", "alice")
- log → ["A:alice", "B:alice"]

**Explanation**: Two handlers registered; both called in subscription order

### Example 3: Dispatch with no handlers

**Operations**:
- dispatch("nonexistent_event", "data")
- (no error; nothing happens)

**Explanation**: Dispatching an unregistered event is a no-op

### Example 4: Multiple events

**Operations**:
- log = []
- subscribe("start", handler that appends "start:" + data to log)
- subscribe("stop", handler that appends "stop:" + data to log)
- dispatch("start", "service_1")
- dispatch("stop", "service_1")
- log → ["start:service_1", "stop:service_1"]

**Explanation**: Two separate events, each with one handler; dispatched independently

### Example 5: Unsubscribe removes handler

**Operations**:
- log = []
- subscribe("event", handler_A that appends "A" to log)
- subscribe("event", handler_B that appends "B" to log)
- unsubscribe("event", handler_A)
- dispatch("event", None)
- log → ["B"]

**Explanation**: After unsubscribing handler_A, only handler_B is called

### Example 6: Clear removes all handlers

**Operations**:
- log = []
- subscribe("event", handler_A that appends "A" to log)
- subscribe("event", handler_B that appends "B" to log)
- clear("event")
- dispatch("event", None)
- log → []

**Explanation**: After clear(), dispatch does nothing

### Example 7: Same handler subscribed twice

**Operations**:
- count = [0]
- subscribe("ping", handler that increments count[0])
- subscribe("ping", handler that increments count[0])
- dispatch("ping", None)
- count → [2]

**Explanation**: Same handler subscribed twice; both subscriptions are called

## Test Cases

### Required Coverage

- Single handler called with correct data
- Multiple handlers called in subscription order
- Dispatch with no handlers registered (no error)
- Different events are independent (dispatching one does not trigger another)
- unsubscribe removes one handler registration
- unsubscribe on non-registered handler does nothing
- clear removes all handlers for an event
- clear on non-registered event does nothing
- Same handler subscribed twice (both registrations fire)
- Data of different types passed correctly (string, number, null/none)
- Handler can call dispatch internally (re-entrant dispatch)

### Minimum Test Count

11 test cases

## Success Criteria

- [ ] Handlers called in registration order
- [ ] All registered handlers receive correct data argument
- [ ] Dispatch on unregistered event name does nothing
- [ ] unsubscribe removes exactly one handler registration
- [ ] clear removes all handlers for the event
- [ ] Same handler subscribed twice fires twice per dispatch
- [ ] Events are independent of each other

## Notes

**Common Mistakes**:
- Calling handlers in reverse order (registration order must be preserved — use a list, not a stack)
- Modifying the handler list while iterating during dispatch (if a handler calls unsubscribe during dispatch, naive implementations may skip or repeat handlers — copy the list before iterating to be safe)
- Raising an error when dispatching to an event with no handlers (should silently do nothing)
- unsubscribe removing all occurrences of a handler instead of just the first

**Internal Structure**:
Maintain a map from event_name to an ordered list of handlers. subscribe appends to the list. dispatch iterates the list (on a copy to handle re-entrant modification). unsubscribe finds and removes the first matching entry. clear removes the entire list entry.

**Handler Identity**:
Comparing handlers for unsubscribe requires equality comparison of the callable objects. In languages where callable equality is by reference/identity, this works naturally. In others, the handler passed to unsubscribe must be the same object reference that was passed to subscribe.
