# BS-M-039: Thread-Safe Counter

**Tier**: Medium
**Category**: Concurrency
**Estimated LOC**: 35-50

## Task Description

Implement a counter that supports increment, decrement, and value retrieval operations that are safe to use from multiple concurrent threads. The counter must guarantee that no updates are lost and that the value read always reflects a consistent state, even when multiple threads operate simultaneously.

## Requirements

### Functional Requirements

1. **increment()**: Increase the counter value by 1 atomically
2. **decrement()**: Decrease the counter value by 1 atomically
3. **get()**: Return the current counter value
4. **reset()**: Set the counter back to 0 atomically
5. Create the counter with an initial value of 0 (or an optionally specified initial value)
6. All operations must be safe for concurrent access by multiple threads — no updates may be lost due to race conditions

### Concurrency Requirements

- Concurrent increment() calls from multiple threads must each take effect exactly once (no lost updates)
- Concurrent decrement() calls from multiple threads must each take effect exactly once
- Mixed concurrent increment and decrement calls must produce a final value equal to the net sum of all operations
- get() may be called concurrently with increment()/decrement(); it must return a value that was valid at some point during its execution (does not need to reflect changes that occurred after it started)

### Input Specification

- **initial_value** (optional): An integer — starting value (default 0)
- **increment()**: No parameters; returns nothing
- **decrement()**: No parameters; returns nothing
- **get()**: No parameters; returns an integer — the current value
- **reset()**: No parameters; returns nothing

### Constraints

- Counter value: any integer (may go negative if decrements exceed increments)
- Thread count for testing: up to 100 concurrent threads
- Operation count per test: up to 10,000 operations per thread
- Use the synchronization primitives available in the target language (mutex, lock, atomic operations, etc.)
- Do not implement busy-waiting (spin loops) as the sole synchronization mechanism

## Examples

### Example 1: Sequential operations (baseline correctness)

**Operations** (single thread):
- increment() × 5
- decrement() × 2
- get() → 3

**Explanation**: 5 increments minus 2 decrements = 3; sequential correctness is the minimum requirement

### Example 2: Concurrent increments

**Setup**: Start 10 threads, each calling increment() 100 times
**Expected get() after all threads complete**: 1000
**Explanation**: 10 threads × 100 increments = 1000 total; thread-safe implementation loses no updates

### Example 3: Concurrent increments and decrements

**Setup**: Start 5 threads each calling increment() 100 times; simultaneously start 5 threads each calling decrement() 100 times
**Expected get() after all threads complete**: 0
**Explanation**: Equal increments and decrements cancel out; net change is 0

### Example 4: Reset during concurrent operations

**Operations**:
- Increment to 50 (single thread)
- reset()
- get() → 0

**Explanation**: Reset brings value back to 0; concurrent safety of reset is also required

### Example 5: Large concurrent load

**Setup**: Start 100 threads, each calling increment() 1000 times
**Expected get() after all threads complete**: 100,000
**Explanation**: Under high load, no increments are lost; correctness maintained

### Example 6: Initial value

**Operations**:
- Create counter with initial_value = 10
- increment() × 3
- get() → 13

**Explanation**: Starting from 10, three increments bring it to 13

## Test Cases

### Required Coverage

- Sequential increment correctness
- Sequential decrement correctness
- Sequential mixed operations (net sum correct)
- get() returns 0 for fresh counter
- reset() sets value to 0
- Concurrent increments from multiple threads (final value = thread_count × ops_per_thread)
- Concurrent decrements from multiple threads
- Mixed concurrent increments and decrements (net result correct)
- reset() followed by concurrent operations
- Counter with non-zero initial value
- High contention: many threads, many operations per thread

### Minimum Test Count

11 test cases

## Success Criteria

- [ ] Sequential operations produce correct results
- [ ] Concurrent increments: no updates lost (final value matches expected)
- [ ] Concurrent decrements: no updates lost
- [ ] Mixed concurrent operations: net result correct
- [ ] reset() works correctly in both sequential and concurrent contexts
- [ ] get() returns a valid value under concurrent modification
- [ ] Implementation uses proper synchronization (not busy-waiting)

## Notes

**Common Mistakes**:
- Using a simple read-modify-write without synchronization — creates a race condition where two threads read the same value, both increment it, and one update is lost (this is the classic lost-update bug)
- Locking only get() but not increment()/decrement() — all operations that access shared state must be synchronized
- Using a lock that is not properly released on all code paths
- Forgetting that even a single integer read-modify-write is not atomic on most hardware without explicit atomics

**Synchronization Approaches**:
1. **Mutex/Lock**: Wrap each operation in a mutex lock. Simple and correct.
2. **Atomic integer**: Use the language's built-in atomic integer type if available. Lower overhead for high contention.
3. **Compare-and-swap loop**: Manually implement CAS loop — acceptable but more complex.

**Testing Concurrency**:
Race condition bugs are non-deterministic. Correct tests run operations on many threads (e.g., 50–100 threads × 1000 ops) and assert the final value. A broken implementation will occasionally produce wrong results; a correct one will always produce the right value.

**Language Note**: The spec is language-agnostic — use whatever thread/synchronization primitives the target language provides (threads + mutex, goroutines + mutex, Java synchronized, Rust Mutex, etc.).
