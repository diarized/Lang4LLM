# BS-C-015: Config File System

**Tier**: Complex
**Category**: File I/O
**Estimated LOC**: 90-120

## Task Description

Implement a hierarchical configuration system that loads key-value settings from a plain-text file format supporting sections and nested keys, exposes values via dot-notation access paths (such as "database.host" or "server.port"), allows setting and overriding values in memory, and serializes the current state back to the same text format.

## Requirements

### Functional Requirements

1. Support `load(text)` that parses a configuration text string and returns a configuration object
2. Support `get(config, path)` that retrieves the value at the given dot-notation path; return null/none if the path does not exist
3. Support `set(config, path, value)` that sets or overwrites the value at the given dot-notation path in the in-memory configuration
4. Support `save(config)` that serializes the current configuration state back to the text format and returns the text string
5. The text format uses `[section]` headers to group keys; keys within a section are accessed as `section.key`
6. Keys outside any section header belong to a root-level namespace and are accessed by their name directly
7. Nested keys (more than two levels) are supported by allowing dot-separated key names within a section, accessed as `section.subkey.leaf`
8. Values are stored as text strings; interpretation as numbers or booleans is the caller's responsibility

### Input Specification

- **text (for load)**: A multi-line text string in the following format:
  - Blank lines and lines beginning with `#` are comments and ignored
  - A line of the form `[section_name]` begins a new section
  - A line of the form `key = value` assigns the value (text after first `=`, trimmed) to the key within the current section
  - Keys before any section header belong to the root namespace
- **path (for get/set)**: A dot-separated string of identifiers; e.g., `"database.host"` or `"timeout"` or `"app.logging.level"`
- **value (for set)**: A text string
- **Return of get**: Text string value, or null/none if path not found
- **Return of save**: Text string in the config file format

### Constraints

- Section names and key names contain only alphanumeric characters and underscores
- Values may contain any printable characters including spaces and dots
- Duplicate keys within the same section: last definition wins
- Maximum nesting depth via dot-separated keys: at least 3 levels
- No external configuration parsing libraries allowed
- Round-trip: `save(load(text))` must produce semantically equivalent output (same keys and values, though order and whitespace may differ)

## Examples

### Example 1: Loading and accessing values

**Input text**:
```
# Application configuration
app_name = MyApp

[database]
host = localhost
port = 5432
name = production_db

[server]
host = 0.0.0.0
port = 8080
```

**Operations**:
```
config = load(text)
get(config, "app_name")       // returns "MyApp"
get(config, "database.host")  // returns "localhost"
get(config, "database.port")  // returns "5432"
get(config, "server.port")    // returns "8080"
get(config, "missing.key")    // returns null
```

**Explanation**:
- Root-level key `app_name` accessed directly
- Section keys accessed as `section.key`
- Missing paths return null without error

### Example 2: Setting values and save round-trip

**Operations**:
```
config = load("")              // start with empty config
set(config, "app.name", "Demo")
set(config, "app.version", "1.0")
set(config, "timeout", "30")
output = save(config)
```

**Expected output** (content equivalent, order may vary):
```
timeout = 30

[app]
name = Demo
version = 1.0
```

**Explanation**:
- Root-level keys appear before section blocks
- Keys set via dot-notation are grouped into their section
- save produces parseable output (load(save(config)) yields same values)

### Example 3: Override existing value

**Operations**:
```
config = load("[db]\nhost = old_host\nport = 3306")
get(config, "db.host")         // returns "old_host"
set(config, "db.host", "new_host")
get(config, "db.host")         // returns "new_host"
get(config, "db.port")         // returns "3306"  (unchanged)
```

**Explanation**:
- set overwrites existing values without affecting other keys
- Other keys in the same section remain intact

### Example 4: Deeply nested key via dot-notation in key name

**Input text**:
```
[logging]
file.path = /var/log/app.log
file.level = DEBUG
console.level = INFO
```

**Operations**:
```
config = load(text)
get(config, "logging.file.path")    // returns "/var/log/app.log"
get(config, "logging.file.level")   // returns "DEBUG"
get(config, "logging.console.level") // returns "INFO"
```

**Explanation**:
- Key `file.path` within section `[logging]` is accessed as `logging.file.path`
- The dot in the key name extends the path depth to 3 levels

## Test Cases

2. Get a root-level key (no section prefix)
3. Get a section-scoped key using dot-notation
4. Get a non-existent key returns null/none
5. Get a non-existent section returns null/none
6. Set a new root-level key; verify get returns it
7. Set a new key in a new section; verify get returns it
8. Set overrides an existing key; verify old value replaced
9. Set does not affect sibling keys in the same section
10. Save produces text that round-trips correctly through load
11. Comments and blank lines in input are ignored during load
12. Duplicate key in same section: last value wins
13. Deeply nested path (3 levels) via dot-separated key name within section
14. Load empty string produces empty config (all gets return null)
15. Save empty config produces valid (possibly empty) output that loads cleanly

### Minimum Test Count

12 test cases

## Success Criteria

- [ ] get returns correct value for all root-level and section-scoped paths
- [ ] get returns null for any path that does not exist
- [ ] set creates new keys and overrides existing keys correctly
- [ ] set does not disturb unrelated keys in the same or other sections
- [ ] save produces text that re-parses to the same set of values (round-trip)
- [ ] Comments and blank lines in input do not affect loaded values
- [ ] Duplicate key handling: last definition wins

## Notes

**Implementation Strategies**:

- Internal representation: a nested dictionary/map; section name maps to another map of key-to-value pairs; root-level keys stored under a reserved root namespace key (e.g., empty string or a sentinel)
- Parsing: iterate lines, track current section, split on first `=` for key-value pairs
- get: split path by `.`; first segment is section name (or root if single segment); remaining segments reconstruct the key name
- set: split path the same way; create intermediate section if absent
- save: emit root-level keys first, then each section with its `[section]` header and key-value lines

**Format Ambiguity Resolution**:
- When a dot appears in a key name within a section, the path interpretation is: first segment is the section, remaining segments join back to form the full key name as stored
- This means internally, within a section, the key can be stored as `"file.path"` (string with dot), or recursively nested — choose one representation and apply consistently

**Common Mistakes**:
- Splitting the path on the wrong separator (using `.split(".")` naively without accounting for keys that contain dots in their stored form)
- Overwriting an entire section when setting a single key (destroying sibling keys)
- Round-trip failure: save does not emit all keys that were set programmatically
- Not trimming whitespace from keys and values during parsing
- Ignoring comment lines that start with `#` but also contain valid-looking `=`

**Edge Cases**:
- Value string containing `=` character (split on first `=` only)
- Key name or section name containing only underscores
- Setting a path that creates a new section not present in the original loaded text
