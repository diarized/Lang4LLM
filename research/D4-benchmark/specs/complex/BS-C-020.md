# BS-C-020: Rate Limiter (Token Bucket)

**Tier**: Complex
**Category**: Concurrency
**Estimated LOC**: 80-110

## Task Description

Implement a token bucket rate limiter that controls access to a shared resource. Tokens accumulate in a bucket at a fixed replenishment rate up to a maximum capacity. Callers acquire a specified number of tokens; if insufficient tokens are available, the caller blocks until enough tokens have been replenished. The implementation must be safe for concurrent access by multiple callers.

## Requirements

### Functional Requirements

1. Support `create_limiter(capacity, rate)` that creates a token bucket limiter starting at full capacity, where:
   - `capacity` is the maximum number of tokens the bucket can hold
   - `rate` is the number of tokens added per second (as a real number)
2. Support `acquire(limiter, n)` that acquires exactly `n` tokens from the bucket:
   - If `n` tokens are currently available, consume them and return immediately
   - If fewer than `n` tokens are available, block the calling thread until enough tokens have been replenished, then consume them and return
3. Tokens replenish continuously over time at the given rate; the bucket never exceeds `capacity` tokens
4. Support `try_acquire(limiter, n)` that attempts to acquire `n` tokens without blocking:
   - If `n` tokens are available, consume them and return true
   - If not, return false immediately without modifying the bucket
5. Support `available_tokens(limiter)` that returns the current approximate token count (as a real number)
6. The implementation must be thread-safe: multiple callers may call `acquire` or `try_acquire` concurrently without corrupting the bucket state

### Input Specification

- **capacity**: A positive real number — maximum tokens in the bucket
- **rate**: A positive real number — tokens added per second
- **n (for acquire/try_acquire)**: A positive real number of tokens to acquire; must not exceed capacity
- **acquire(limiter, n)**: Blocking call; returns when n tokens have been consumed
- **try_acquire(limiter, n)**: Non-blocking; returns true if acquired, false otherwise
- **available_tokens(limiter)**: Returns current token count (0.0 to capacity)

### Constraints

- Tokens are real numbers (fractional token counts are valid)
- n must be > 0 and <= capacity; requesting more than capacity is an error
- Token replenishment is computed lazily (recalculated based on elapsed time since last update, not via a background thread) — this is the standard approach
- Multiple concurrent callers to acquire must not result in more tokens consumed than were available
- Blocking in acquire must not use busy-waiting; use appropriate synchronization primitives
- No external rate limiting libraries allowed

## Examples

### Example 1: Basic acquire with sufficient tokens

**Operations**:
```
limiter = create_limiter(capacity=10, rate=1.0)
// Starts full: 10 tokens available

result = try_acquire(limiter, 5)   // true; 5 tokens remain
result = try_acquire(limiter, 6)   // false; only 5 available
result = try_acquire(limiter, 5)   // true; 0 tokens remain
result = try_acquire(limiter, 1)   // false; 0 tokens available
```

**Explanation**:
- try_acquire succeeds only when sufficient tokens are present
- After consuming all tokens, further requests fail immediately

### Example 2: Blocking acquire and replenishment

**Operations**:
```
limiter = create_limiter(capacity=5, rate=2.0)
// rate = 2 tokens/second

try_acquire(limiter, 5)   // consume all 5 tokens

// Now: 0 tokens available
// acquire(limiter, 1) will block for ~0.5 seconds (1/2.0 rate)
acquire(limiter, 1)
// Returns after approximately 0.5 seconds when 1 token has replenished
```

**Explanation**:
- At rate=2 tokens/second, replenishing 1 token takes 0.5 seconds
- acquire blocks the caller until sufficient tokens are available

### Example 3: Token count never exceeds capacity

**Operations**:
```
limiter = create_limiter(capacity=10, rate=5.0)
// Start full at 10

// Wait 10 seconds (would add 50 tokens without cap)
// available_tokens(limiter) == 10.0  (capped at capacity)

acquire(limiter, 10)      // consume all
// available_tokens ~= 0.0 immediately after
```

**Explanation**:
- Bucket does not accumulate tokens beyond capacity regardless of elapsed time

### Example 4: Concurrent callers

**Operations**:
```
limiter = create_limiter(capacity=10, rate=5.0)
results = []
lock = create_mutex()

// Launch 5 concurrent threads, each acquiring 3 tokens
// (total requested: 15 tokens; capacity is 10)
for i in 1..5:
  spawn_thread(function() {
    acquire(limiter, 3)
    acquire(lock); results.append(i); release(lock)
  })

wait_for_all_threads()
// len(results) == 5
// All 5 threads eventually complete as tokens replenish
```

**Explanation**:
- First 3 threads acquire 9 tokens (within capacity)
- Thread 4 acquires 1 remaining + waits for 2 more (blocking)
- Thread 5 waits for 3 tokens to replenish (blocking)
- All eventually complete; results has 5 entries

### Example 5: try_acquire during replenishment

**Operations**:
```
limiter = create_limiter(capacity=4, rate=2.0)
try_acquire(limiter, 4)   // drain completely

// Immediately after:
try_acquire(limiter, 1)   // false (0 tokens, not yet replenished)

// After ~1.0 second:
try_acquire(limiter, 2)   // true (2 tokens have replenished)
try_acquire(limiter, 1)   // false (0 tokens again)
```

**Explanation**:
- try_acquire is a point-in-time check; it does not wait
- Tokens accumulate between calls based on elapsed real time

## Test Cases

### Required Coverage

1. try_acquire succeeds when tokens available; returns true
2. try_acquire fails when insufficient tokens; returns false; bucket unchanged
3. try_acquire with exact available count (boundary: n == available)
4. acquire with sufficient tokens returns immediately
5. acquire blocks when tokens insufficient; returns after replenishment
6. Token count never exceeds capacity (verify after long idle period)
7. Bucket starts at full capacity
8. available_tokens reflects current token count
9. Concurrent try_acquire calls do not double-consume tokens (thread-safety)
10. Concurrent acquire calls do not corrupt bucket state
11. Multiple callers blocked in acquire all eventually complete as tokens replenish
12. n exceeding capacity is rejected as an error
13. Rate=0.1 (slow replenishment): acquire blocks for measurable duration
14. Capacity=1, rate=10: high replenishment rate with minimal capacity

### Minimum Test Count

12 test cases

## Success Criteria

- [ ] acquire blocks when tokens unavailable and returns only after replenishment
- [ ] try_acquire returns true/false without blocking
- [ ] Token count is capped at capacity regardless of elapsed idle time
- [ ] Concurrent access does not result in negative token counts or double-consumption
- [ ] acquire does not use busy-waiting (blocks on synchronization primitive)
- [ ] Requesting n > capacity produces an error
- [ ] available_tokens returns a non-negative value not exceeding capacity

## Notes

**Implementation Strategies**:

**Lazy replenishment**:
- Do not use a background thread to add tokens on a schedule
- Instead, record the timestamp of the last token update
- Whenever the bucket is accessed (acquire, try_acquire, available_tokens):
  1. Compute elapsed time since last update: `delta = current_time - last_update`
  2. Compute tokens to add: `new_tokens = delta * rate`
  3. Set `tokens = min(tokens + new_tokens, capacity)`
  4. Update `last_update = current_time`
  5. Proceed with the check/consume operation

**Mutual exclusion**:
- Protect all bucket state (token count, last_update timestamp) with a mutex
- The token update and consume steps must be atomic with respect to other threads

**Blocking in acquire**:
- After updating tokens, if insufficient: compute wait time = (n - tokens) / rate
- Release the mutex, sleep for the computed duration, re-acquire mutex
- Re-compute tokens after waking (another thread may have consumed some)
- Loop until tokens are sufficient (spurious wake-up protection)

**Common Mistakes**:
- Busy-waiting in acquire (spinning in a loop without sleeping) — violates the no-busy-wait constraint
- Not holding the mutex while updating tokens and consuming — race condition
- Forgetting to re-check token availability after waking from sleep (another thread may have taken them)
- Computing wait time based on token count at time of sleep, but not accounting for concurrent consumption
- Allowing tokens to go negative (should atomically check and consume)
- Not capping at capacity during replenishment (allowing infinite accumulation during idle periods)

**Edge Cases**:
- n = capacity (requesting maximum in one call)
- Capacity = 1 with fractional rate (sub-second replenishment)
- Multiple threads all blocked simultaneously; wake-up ordering may be non-deterministic
- Successive try_acquire calls with zero time elapsed (token count unchanged between calls)
