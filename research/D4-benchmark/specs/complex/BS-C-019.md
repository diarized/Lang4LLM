# BS-C-019: Thread Pool

**Tier**: Complex
**Category**: Concurrency
**Estimated LOC**: 90-120

## Task Description

Implement a fixed-size thread pool that maintains a set of persistent worker threads and a shared task queue. Callers submit tasks (callable units of work) to the pool; workers pick them up and execute them concurrently. The pool supports an ordered shutdown that stops accepting new tasks and waits for all queued tasks to complete before returning.

## Requirements

### Functional Requirements

1. Support `create_pool(size)` that creates a thread pool with exactly `size` persistent worker threads; threads start immediately and wait for tasks
2. Support `submit(pool, task)` that adds a task to the pool's task queue; the task will be executed by one of the worker threads; raises an error if the pool is already shut down
3. Worker threads run a continuous loop: wait for a task, execute it, then wait for the next task
4. Support `shutdown(pool)` that signals the pool to stop accepting new tasks and waits until all currently queued and in-progress tasks have completed, then terminates worker threads
5. After `shutdown` returns, all submitted tasks are guaranteed to have completed
6. Tasks submitted after `shutdown` has been called must be rejected with an error (not silently dropped)
7. Support `wait_all(pool)` that blocks the caller until all currently queued tasks are complete, without shutting down the pool (pool remains usable after wait_all returns)

### Input Specification

- **size**: A positive integer (1 to 64) — number of worker threads
- **task**: A callable that accepts no arguments and returns nothing; may raise exceptions (exceptions from tasks must not crash worker threads — they should be caught and discarded or logged)
- **submit(pool, task)**: Enqueues task; returns immediately (non-blocking); raises error if pool is shut down
- **shutdown(pool)**: Blocking call; returns only after all tasks have completed and threads have terminated
- **wait_all(pool)**: Blocking call; returns only after all submitted tasks have completed; pool remains usable

### Constraints

- Worker threads run concurrently (genuinely parallel execution if platform supports it)
- Task queue is unbounded (no rejection due to queue size)
- Tasks must not starve: if a worker is free and a task is queued, the worker must pick it up
- Exceptions thrown inside a task must not kill the worker thread
- No busy-waiting loops allowed (workers must block on a synchronization primitive)
- No external thread pool libraries allowed; must implement using primitive threading and synchronization constructs

## Examples

### Example 1: Basic parallel task execution

**Operations**:
```
results = []
lock = create_mutex()

pool = create_pool(size=3)

for i in 1..9:
  task = function() {
    acquire(lock)
    results.append(i)
    release(lock)
  }
  submit(pool, task)

shutdown(pool)
// After shutdown: results contains all of 1..9 (order may vary)
// len(results) == 9
```

**Explanation**:
- 9 tasks submitted to a 3-worker pool
- Workers execute tasks concurrently; exact order is non-deterministic
- After shutdown, all 9 tasks have run

### Example 2: Submit after shutdown raises error

**Operations**:
```
pool = create_pool(size=2)
submit(pool, function() { /* work */ })
shutdown(pool)

submit(pool, function() { /* more work */ })
// Error: pool is shut down, submission rejected
```

**Explanation**:
- Once shutdown is called, the pool does not accept new tasks

### Example 3: wait_all preserves pool usability

**Operations**:
```
counter = 0
lock = create_mutex()
pool = create_pool(size=2)

for i in 1..4:
  submit(pool, function() {
    acquire(lock); counter += 1; release(lock)
  })

wait_all(pool)
// counter == 4 (all four tasks completed)

// Pool still usable:
submit(pool, function() {
  acquire(lock); counter += 1; release(lock)
})
wait_all(pool)
// counter == 5

shutdown(pool)
```

**Explanation**:
- wait_all blocks until all tasks are done
- After wait_all, pool is still active and can accept more tasks

### Example 4: Task exception does not crash pool

**Operations**:
```
results = []
lock = create_mutex()
pool = create_pool(size=2)

submit(pool, function() { raise Error("intentional failure") })
submit(pool, function() {
  acquire(lock); results.append("ok"); release(lock)
})

shutdown(pool)
// results = ["ok"]
// Pool completed successfully despite the exception in task 1
```

**Explanation**:
- Worker caught the exception from task 1, discarded it, and continued
- Task 2 still executed normally

### Example 5: Pool with size 1 (sequential execution)

**Operations**:
```
sequence = []
pool = create_pool(size=1)

submit(pool, function() { sequence.append(1) })
submit(pool, function() { sequence.append(2) })
submit(pool, function() { sequence.append(3) })

shutdown(pool)
// sequence = [1, 2, 3]  (guaranteed order with single worker)
```

**Explanation**:
- Single-worker pool processes tasks in FIFO order

## Test Cases

### Required Coverage

1. Submit N tasks to pool of size S; verify all N tasks complete after shutdown
2. Tasks execute concurrently (pool size > 1; use timing or counters to verify overlap)
3. Submit after shutdown raises an error
4. Pool size 1 executes tasks in FIFO order
5. wait_all blocks until all current tasks are done without shutting down pool
6. Pool remains usable after wait_all (submit more tasks)
7. Task that raises an exception does not crash the worker
8. Worker continues accepting tasks after exception-throwing task
9. Large number of tasks (100+) all complete correctly
10. Pool size equals task count (each worker handles exactly one task)
11. Pool size larger than task count (some workers idle the entire time)
12. Shutdown waits for in-progress tasks to complete (not just queued tasks)
13. shutdown is idempotent or safe to call on an already-shut-down pool (no double-shutdown crash)

### Minimum Test Count

12 test cases

## Success Criteria

- [ ] All submitted tasks complete before shutdown returns
- [ ] Worker threads block (not busy-wait) when no tasks are available
- [ ] Task exceptions are caught and do not terminate worker threads
- [ ] Submit after shutdown raises an error (tasks not silently dropped)
- [ ] wait_all blocks until all tasks complete and pool remains usable afterward
- [ ] FIFO task ordering guaranteed for pool size 1
- [ ] No data races on shared pool state (submit, shutdown, wait_all are thread-safe)

## Notes

**Implementation Strategies**:

**Core components**:
- **Task queue**: A thread-safe blocking queue (mutex + condition variable); workers block on an empty queue
- **Worker threads**: Each runs a loop — wait for task (blocking), execute task, repeat; exit when a sentinel/shutdown signal is received
- **Shutdown mechanism**: Two-phase:
  1. Set a "shutdown" flag; enqueue one sentinel (null/stop signal) per worker so each wakes up and sees the shutdown
  2. Join all worker threads (blocking until each finishes its current task and exits the loop)

**wait_all pattern**:
- Track pending task count with an atomic counter or condition variable
- Increment before submit; decrement after task completes
- wait_all blocks until counter reaches zero

**Thread-safe queue**:
- Protect the queue with a mutex
- Use a condition variable for workers to wait on (avoid busy polling)
- Notify condition variable on each submit

**Common Mistakes**:
- Busy-waiting workers (spinning in a loop checking the queue) instead of blocking on a condition variable
- Not joining worker threads in shutdown (returns before workers finish)
- Forgetting to handle the case where wait_all is called when no tasks are pending (should return immediately)
- Task queue operations not protected by a lock (race conditions on push/pop)
- Shutdown sends wrong number of sentinel signals (one per worker required)
- Exceptions from tasks propagating out of the worker loop and killing the thread

**Edge Cases**:
- Pool of size 1: sequential; verify FIFO ordering
- Zero tasks submitted before shutdown: safe to call shutdown immediately
- wait_all called with empty queue: must return immediately, not block forever
