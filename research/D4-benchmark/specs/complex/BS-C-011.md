# BS-C-011: Balanced Bracket Validator with Error Location

**Tier**: Complex
**Category**: String Processing
**Estimated LOC**: 60-90

## Task Description

Implement a bracket validator that checks whether a string containing round parentheses, square brackets, and curly braces is balanced. If the string is balanced, return a success result. If it is not balanced, return the 0-based index in the string of the first unmatched or mismatched bracket along with a description of the error type. Non-bracket characters in the input are ignored.

## Requirements

### Functional Requirements

1. Scan the input string character by character, treating "(", "[", "{" as opening brackets and ")", "]", "}" as closing brackets; all other characters are skipped
2. Determine whether all brackets are correctly nested and matched
3. If balanced, return a success result indicating no error
4. If not balanced, return the 0-based index (in the original string, including non-bracket characters) of the first bracket that causes an imbalance, and classify the error as one of:
   - **UNMATCHED_OPEN**: An opening bracket that is never closed (detected at end of string)
   - **UNMATCHED_CLOSE**: A closing bracket with no corresponding opening bracket
   - **MISMATCH**: A closing bracket that does not match the most recent unmatched opening bracket (e.g., "(" closed by "]")
5. When multiple errors could be detected, report the earliest one (leftmost position in the string)
6. After returning the first error, do not require reporting subsequent errors

### Input Specification

- **text**: A string — may contain any printable characters; length 0 to 10,000
- **Return**: Either:
  - A success indicator (e.g., true, or a result object with no error)
  - An error result containing:
    - **index**: A non-negative integer — the 0-based position in the input string of the problematic bracket
    - **error_type**: One of UNMATCHED_OPEN, UNMATCHED_CLOSE, or MISMATCH

### Constraints

- Input length: 0 to 10,000 characters
- The three bracket types must be treated as distinct pairs: "()" is valid, "(]" is a mismatch
- Non-bracket characters do not affect bracket validity but do count toward character indices
- Empty string is considered balanced
- Multiple consecutive unmatched opening brackets: the first one opened is the first unmatched (report the leftmost)

## Examples

### Example 1: Balanced strings

**Input**: "()"
**Output**: success

**Input**: "([{}])"
**Output**: success

**Input**: "a(b[c]d)e"
**Output**: success (non-bracket characters ignored for balancing but counted for indexing)

**Input**: ""
**Output**: success

### Example 2: Unmatched close — no open bracket

**Input**: ")"
**Output**: error at index 0, type UNMATCHED_CLOSE

**Input**: "abc]def"
**Output**: error at index 3, type UNMATCHED_CLOSE

**Explanation**: "]" at position 3 has no corresponding "[" open before it.

### Example 3: Mismatch — wrong closing bracket type

**Input**: "(]"
**Output**: error at index 1, type MISMATCH

**Input**: "([)]"
**Output**: error at index 2, type MISMATCH

**Explanation**:
- In "(]": the open "(" at index 0 is on the stack; "]" at index 1 expects "[" — mismatch
- In "([)]": after "(", "[", the ")" at index 2 expects "]" but finds "(" on stack — mismatch at index 2

### Example 4: Unmatched open — never closed

**Input**: "("
**Output**: error at index 0, type UNMATCHED_OPEN

**Input**: "(()("
**Output**: error at index 3, type UNMATCHED_OPEN

**Explanation**:
- "(()(" has the outer "(" at index 0 and the extra "(" at index 3 unmatched
- The first unmatched open bracket is the one at index 3 because the pair at indices 1-2 is matched; however, index 0 is also unmatched
- The earliest unmatched open is determined at end-of-string by the bottom of the stack: report the one at the bottom (index 0), not the top

**Clarification for Example 4**:
- Stack after scanning "(()(" left to right: push index 0, push index 1, pop on ")" at index 2 (matched), push index 3
- At end, stack contains [index 0, index 3]
- The earliest unmatched open bracket is the one at index 0 (bottom of stack)

### Example 5: Non-bracket characters

**Input**: "hello (world [!])"
**Output**: success

**Input**: "hi (there]"
**Output**: error at index 9, type MISMATCH

**Explanation**: The "]" is at string index 9 (counting all characters including spaces). The open "(" at index 3 expects ")" but finds "]".

### Example 6: Multiple open brackets, first unmatched

**Input**: "((("
**Output**: error at index 0, type UNMATCHED_OPEN

**Explanation**: All three are unmatched; the first one (index 0) is reported.

## Test Cases

### Required Coverage

1. Empty string returns success
2. Single matched pair "()" returns success
3. Correctly nested brackets "([{}])" returns success
4. Non-bracket characters mixed in, still balanced
5. Single unmatched closing bracket ")" → UNMATCHED_CLOSE at index 0
6. Closing bracket with no prior open in mixed string → UNMATCHED_CLOSE with correct index
7. Mismatched type "(]" → MISMATCH at index of closing bracket
8. Mismatched type "([)]" → MISMATCH at first wrong closer
9. Single unclosed open "(" → UNMATCHED_OPEN at index 0
10. Multiple unclosed opens, report the earliest (leftmost) one
11. Correctly matched pairs followed by unclosed open "()[]{" → UNMATCHED_OPEN at index of "{"
12. Non-bracket characters counted toward index (correct index for bracket in the middle of text)
13. String with only non-bracket characters returns success
14. All three bracket types mixed and correctly balanced
15. Deeply nested balanced brackets (10+ levels)

### Minimum Test Count

15 test cases

## Success Criteria

- [ ] Balanced strings always return success regardless of nesting depth or bracket type mix
- [ ] UNMATCHED_CLOSE reported at the exact index of the first closing bracket with no opener
- [ ] MISMATCH reported at the exact index of the first closing bracket that does not match opener type
- [ ] UNMATCHED_OPEN reports the index of the earliest (leftmost) unmatched opening bracket
- [ ] Non-bracket characters are ignored for balance logic but included in index counting
- [ ] Empty string returns success
- [ ] All three bracket pair types are treated as distinct (cannot cross-match)

## Notes

**Implementation Strategy — Stack-Based Validation**:
- Maintain a stack of (bracket_character, original_index) pairs
- Scan each character in the input string, tracking the current index
- When an opening bracket is encountered: push (character, index) onto the stack
- When a closing bracket is encountered:
  - If the stack is empty: return UNMATCHED_CLOSE at the current index
  - Pop the top of the stack; if the opener does not match the closer type: return MISMATCH at the current index
  - Otherwise: the pair is matched, continue
- After scanning the entire string:
  - If the stack is empty: return success
  - Otherwise: the bottom of the stack holds the earliest unmatched opener; return UNMATCHED_OPEN at that index

**Matching Bracket Pairs**:
- "()" — round parentheses
- "[]" — square brackets
- "{}" — curly braces
- Maintain a lookup so that given a closing bracket, you can retrieve its expected opener

**Reporting the Earliest UNMATCHED_OPEN**:
- When the scan is complete and the stack is non-empty, the bottom of the stack (first element pushed) is the earliest unmatched opener
- Report its stored original index

**Common Mistakes**:
- Reporting the top of the stack (most recent opener) instead of the bottom (earliest opener) for UNMATCHED_OPEN
- Not counting non-bracket characters in the index (producing off-by-one or wrong indices)
- Treating different bracket types as interchangeable ("(" matched with "]" considered valid)
- Returning MISMATCH instead of UNMATCHED_CLOSE when the stack is empty and a closer is found
- Not resetting the stack between test cases (if reusing the same validator object)
- Forgetting the case where the closing bracket is correct type but stack is empty (UNMATCHED_CLOSE, not MISMATCH)
