# BS-C-016: Observer Pattern

**Tier**: Complex
**Category**: Object-Oriented Design
**Estimated LOC**: 70-100

## Task Description

Implement an observable subject and observer infrastructure where observers can subscribe to and unsubscribe from named event types, and the subject notifies all registered observers with event data when its state changes. The implementation must support multiple independent event types and multiple observers per event type.

## Requirements

### Functional Requirements

1. Support creating a subject (observable entity) that maintains internal state and a registry of observers per event type
2. Support `subscribe(subject, event_type, observer)` that registers an observer to receive notifications for a specific event type
3. Support `unsubscribe(subject, event_type, observer)` that removes a previously registered observer from a specific event type; no error if observer was not registered
4. Support `notify(subject, event_type, data)` that invokes all observers currently registered for that event type, passing the event data to each
5. Observers are callable units (functions or objects with a callable interface) that accept the event data as their argument
6. Support multiple observers registered for the same event type; all are notified in the order they were registered
7. Support multiple event types on the same subject; notifications for one event type do not trigger observers of another
8. Unsubscribing an observer from one event type must not affect its registrations for other event types
9. Notifying an event type with no registered observers must succeed silently (no error)

### Input Specification

- **subject**: An object managing a registry of event type → list of observers
- **event_type**: A text string identifying the event category (e.g., "click", "data_changed", "error")
- **observer**: A callable that accepts a single argument (the event data); must support equality comparison so it can be located for unsubscription
- **data**: Any value passed through to observers; the subject does not interpret it
- **notify(subject, event_type, data)**:
  - Calls each registered observer for the event type with data as the argument
  - Calls them in subscription order
  - Returns nothing (or a count of observers notified)

### Constraints

- At least 2 distinct event types must be demonstrably independent
- Subscribing the same observer twice to the same event type: it may be called once or twice per notification depending on implementation, but behavior must be documented and consistent
- No observer should affect other observers during a notification round (no mid-iteration mutation of the observer list)
- No external event/signal libraries allowed

## Examples

### Example 1: Basic subscribe and notify

**Operations**:
```
subject = create_subject()
log = []

observer_A = function(data) { log.append("A:" + data) }
subscribe(subject, "update", observer_A)

notify(subject, "update", "hello")
// log = ["A:hello"]

notify(subject, "update", "world")
// log = ["A:hello", "A:world"]
```

**Explanation**:
- observer_A is called each time "update" is notified
- Data is passed through unchanged

### Example 2: Multiple observers, notification order

**Operations**:
```
subject = create_subject()
calls = []

obs1 = function(data) { calls.append("obs1") }
obs2 = function(data) { calls.append("obs2") }
obs3 = function(data) { calls.append("obs3") }

subscribe(subject, "change", obs1)
subscribe(subject, "change", obs2)
subscribe(subject, "change", obs3)

notify(subject, "change", null)
// calls = ["obs1", "obs2", "obs3"]
```

**Explanation**:
- All three observers are notified in registration order

### Example 3: Unsubscribe

**Operations**:
```
subject = create_subject()
calls = []

obs1 = function(data) { calls.append("obs1") }
obs2 = function(data) { calls.append("obs2") }

subscribe(subject, "tick", obs1)
subscribe(subject, "tick", obs2)

notify(subject, "tick", 1)
// calls = ["obs1", "obs2"]

unsubscribe(subject, "tick", obs1)
notify(subject, "tick", 2)
// calls = ["obs1", "obs2", "obs2"]
```

**Explanation**:
- After unsubscribing obs1, only obs2 is notified on the second tick
- obs1's prior calls are unaffected

### Example 4: Multiple independent event types

**Operations**:
```
subject = create_subject()
clicks = []
errors = []

on_click = function(data) { clicks.append(data) }
on_error = function(data) { errors.append(data) }

subscribe(subject, "click", on_click)
subscribe(subject, "error", on_error)

notify(subject, "click", "button1")
notify(subject, "error", "timeout")
notify(subject, "click", "button2")

// clicks = ["button1", "button2"]
// errors = ["timeout"]
```

**Explanation**:
- click and error event types are fully independent
- Notifying "click" does not affect "error" observers

### Example 5: Notify with no observers

**Operations**:
```
subject = create_subject()
notify(subject, "unknown_event", "data")
// No error — succeeds silently
```

**Explanation**:
- Notifying an event type with zero registered observers is a no-op

## Test Cases

### Required Coverage

1. Subscribe one observer; verify it is called on notify
2. Subscribe two observers to same event; verify both called in order
3. Subscribe three observers; verify registration order preserved on notify
4. Unsubscribe one observer from event; verify it is no longer called
5. Unsubscribe observer not registered (no error expected)
6. Unsubscribe from one event type; verify subscription to other event type unaffected
7. Two independent event types; notifying one does not trigger the other
8. Notify an event type with no observers (silent success)
9. Notify passes data argument unchanged to each observer
10. Subscribe same observer to two different event types; unsubscribe from one; verify still active on other
11. Multiple notifies in sequence; observers called correct number of times
12. Create two independent subjects; verify observers do not cross subjects

### Minimum Test Count

12 test cases

## Success Criteria

- [ ] Observers are called in registration order during notify
- [ ] Unsubscribed observers are not called in subsequent notifications
- [ ] Event types are fully independent (no cross-type notification leakage)
- [ ] Notifying a non-existent or empty event type completes without error
- [ ] Data is passed through to observers without modification
- [ ] Unsubscribing a non-registered observer produces no error
- [ ] Multiple subjects do not share observer registries

## Notes

**Implementation Strategies**:

- Core data structure: a dictionary mapping event_type string → ordered list of observers
- subscribe: append observer to the list for the given event type (create list if first subscriber)
- unsubscribe: remove first matching observer from the list; ignore if not found
- notify: iterate the observer list for the event type, call each observer with data; use a snapshot of the list to prevent issues if an observer modifies registrations during notification

**Observer Identity**:
- Unsubscription requires locating the observer in the list; equality comparison by reference/identity (same object) is the standard approach
- If the language uses function references, they must be comparable by identity to support unsubscription

**Common Mistakes**:
- Modifying the observer list while iterating during notify (causes skipped or double-called observers)
- Sharing a single observer list across all event types instead of per-event-type lists
- Failing silently vs. raising an error when unsubscribing a non-registered observer (spec says: no error)
- Not preserving registration order (using an unordered collection)

**Design Extension Points** (not required, but common in real implementations):
- Returning a "subscription token" from subscribe for easier unsubscription
- Supporting one-time observers that unsubscribe after first notification
- Priority-ordered notification
